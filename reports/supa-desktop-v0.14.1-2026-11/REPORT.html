Performance investigation • 18 November 2026 • Supa Desktop 0.14.1

Why capacity drops above 500 users

The immediate 503 source is confirmed: the gateway exhausts its 256 active-request permits. The deeper problem appears earlier: at 625 users, requests already take several seconds even though almost none are rejected. The strongest next step is to locate time spent inside the runtime and database connection path, then tune that bottleneck.

Observed boundary: 500 passed; 625 failed. These are individual short runs, not a certified sustainable capacity or an exact maximum. No configuration changes or new load runs were made for this analysis.

6. Recommended experiments, in priority order

1 — Locate the queue and validate baseline

Repeat 500 and 625 with the same instrumentation and restored logical fixture, then profile a bounded 625 run. Attach a request ID and monotonic timestamps for permit wait, upstream connect, runtime dispatch, PostgREST pool checkout, transaction begin, SQL execution, commit, response headers and body completion. Record stage histograms, in-flight work and runtime/thread CPU. Correlate with SQL backend PID, state and wait event. Measure statement counter coverage and wall-clock versus guest-clock behavior.

Decision signal: A stage accounts for the seconds-long first-byte wait. A paired 500 repeat determines whether drift or run order changes the baseline.

2 — Runtime and SQL-pool concurrency

Expose the actual PostgREST database-pool configuration, checked-out count, queue length and acquisition time. If supported by this bundled WASM build, sweep pool sizes 2, 4, 8 and 16 one at a time, keeping max_connections=60 and headroom for auth, metrics and administration. If pool wait stays low, investigate WASM executor scheduling, blocking host calls and shared transaction/connection locks. Do not assume native PostgREST defaults apply to this bundle.

Decision signal: Successful throughput increases and first-byte p95 falls at 625 without more SQL contention, memory pressure or errors. Reverse any change that increases queueing.

3 — Cancellation and overload behavior

Trace a 10-second client timeout through gateway, runtime and SQL. Ensure disconnects and deadline expiry cancel queued work and release permits/transactions. The gateway source has a 120-second upstream header timeout, so verify no abandoned work survives needlessly. After throughput improves, compare request caps 128, 256 and 512 in separate runs. Keep the 2,048 connection budget unchanged initially.

Decision signal: No continued SQL/runtime work from abandoned requests; no permit or idle-transaction accumulation. A larger cap counts as an improvement only if all original latency and error targets pass.

4 — Database cache

After validating WASM shared-memory/address-space support, sweep shared_buffers from 16 MiB to 64, then 128 MiB; consider 256 MiB only if needed. Use the supported project/runtime configuration route and restart verification. Enable I/O timing temporarily if supported, measuring its overhead. Compare cache misses, I/O latency, SQL/commit latency, CPU and RSS at a fixed 625 load.

Decision signal: Measured latency or throughput improves alongside reduced costly reads. An increased cache-hit ratio alone is insufficient; PostgreSQL reads may already hit the OS cache.

5 — WAL and checkpoint behavior

If commit or checkpoint waits are material, test max_wal_size=256 MiB first, then independently test wal_buffers=4 MiB (8 MiB only if justified). Verify settings take effect and that the bundled filesystem supports the allocation. Keep fsync, synchronous_commit and full_page_writes on; record WAL generation, checkpoint timing, WAL sync time and recovery implications.

Decision signal: Tail latency falls at fixed load, without changing durability or masking client errors. One requested checkpoint per short run is a lead, not proof of checkpoint causality.

6 — SQL and instrumentation checks

Capture representative query plans under the same authenticated role and JWT/RLS context, including likes prerequisites and exact-count queries. Compare SQL execution, planning and transaction time rather than relying on cumulative means. Keep existing indexes until a plan identifies a specific gap. Run paired full-metrics versus minimal-metrics/logging trials to quantify observer overhead, retaining gateway counters and resource guards.

Decision signal: A specific query, planner behavior, transaction boundary or collector is shown to consume material time. Any optimization preserves API behavior, RLS, auth, returned fields and benchmark work.

PostgREST documents a distinct SQL pool and pool-acquisition timeout, but its bundled runtime configuration must be checked before using native settings: connection pool. PostgreSQL references: buffer memory, WAL configuration, planner cache estimate, I/O timing, EXPLAIN execution semantics. Proposed sizes are experiment starting points, not tested optimums. Apply one supported change at a time in the benchmark project; do not change unrelated projects.

7. How to establish improved capacity

First repeat the current 500 baseline for 5–10 minutes, watching the rising tail and successful throughput. Repeat 625 with the same settings before and after each candidate fix, ideally in alternating order. Keep a paired baseline with full metrics when testing observer overhead. Once 625 passes, return to 750 and 1,000, then bracket higher points using the same pass criteria. Repeat endpoints and perform a 30-minute soak at the chosen passing point.

A pass requires all seven actions to meet the original p95/p99 and error targets, all configured users to authenticate and finish normally, valid fixture evidence, and no generator or native resource guard failure. A guard failure is an invalid or limited measurement requiring review. Do not improve the published number by increasing client timeouts, adding retries, changing think time, reducing the dataset, removing RLS, weakening password hashing, or disabling durability. Preserve a new configuration/build identity and the original results for each experiment.

8. Scope, provenance and uncertainties

Environment: installed Supa Desktop 0.14.1, native Apple M1 Max, 10 cores / 64 GiB; no Docker or cgroup CPU/memory cap. k6 shares the Mac, with GOMAXPROCS=9, GOGC=150, GOMEMLIMIT=36 GiB. A second, mostly idle project stayed running. Gateway counters and backend totals include both; PostgreSQL metrics are isolated by benchmark project ID d6e75d8811c143a292f6405173b4b0fb. The generator pressure guard stayed clear, but the existing short-run classifications explicitly leave generator headroom and capacity certification unverified.

Fixture: 15,000 accounts, 150,000 posts, 150,000 likes; 1 KiB bodies; 20-row pages. Action weights: public feed 35%, own feed 15%, read 15%, create 5%, like 17%, unlike 5%, edit 8%. Think time 1–5 seconds; sessions 300–900 seconds. Each run uses 30-second ramp, 60-second warmup and 120-second measurement after untimed setup. Measured users perform fresh normal password logins with paced admission and no retries; no authentication failures occurred. Session token lifetime is 3,600 seconds, so token refresh is not exercised by this short measurement.

Chronological order was 500 → 1,000 → 750 → 625. Logical fixture state was restored between points and after completion; account/post/like counts returned to 15,000/150,000/150,000. This does not reset physical bloat, vacuum progress, caches, WAL/checkpoint history or runtime age. Early point audits recorded cleanup as pending/false before the subsequent restoration completed; the final gateway audits and combined RESULTS.json record verified cleanup. Runs are single observations, and sampled CPU, descriptors and waits can miss short spikes.
